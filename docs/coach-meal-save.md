# AI饮食确认保存

AI回答中的份量结果形成结构化mealDraft，存入本人assistant聊天记录，返回同一聊天id作为draftId。卡片逐项显示候选食物、份量、基础重量和热量，多个候选必须由用户明确选定；用户选择日期与早餐/午餐/晚餐/加餐，点击确认后才提交。

record.saveCoachMeal只接受draftId、候选下标、日期和餐次。食物名称、重量、营养素从服务端本人聊天草稿读取，不信任客户端传入热量。日期/餐次/候选/总量检查通过后，一条加锁CTE语句原子插入全部食物并标记聊天savedMeal。每项记录id按账号+草稿id+项序号计算；同一草稿重复确认或网络重试返回原保存结果，不重复记账。其他账号不能访问草稿。

克与毫升食物分别生成记录，不把两种单位加成一个重量。每项保留营养素、份量文字、估算标记和草稿来源；现有每日汇总与饮食页直接读取这些记录。已保存状态随聊天历史恢复，保存失败保留卡片供重试。删除饮食记录后，该草稿仍视为已确认，若需再次记账应生成新草稿。

AI只计算不会自动保存；未知/模糊候选不能偷偷选一个并落库。输出未通过安全检查时不返回可保存草稿。历史纯文字回答无结构化草稿，不显示保存按钮。

测试：19项相关测试通过，涵盖账号隔离、候选/日期/餐次验证、稳定记录id、重试返回原餐次、原子SQL、客户端重复提交拦截及历史状态恢复。

云端复测：真实AI生成两项草稿，确认后保存到2026-11-24午餐，两条合计780kcal；更改日期/餐次重复请求仍返回原午餐且只有两条记录。刷新聊天恢复savedMeal。测试创建的两条饮食记录已清理；两种主题卡片均已检查。

## 保存前编辑

草稿候选携带服务端生成的foodSnapshot（每100g/ml营养数据）和portionOptions（可用单位与重量）。客户端与record共用shared/food-portions/meal-editor.js；修改数量和单位立即计算每项重量、热量、营养素与合计。切换单位会重置为1个/碗或100g/ml，并清楚展示数值。无效数量禁用确认。

saveCoachMeal的edits仅含quantity与portionId；服务端从本人草稿的快照重新计算，不信任客户端热量或克数。保存标记保留choices、edits和最终各项摘要，刷新聊天后恢复最终数值。AI原回答为当时计算，页面注明以修改后的卡片为准。

旧草稿无每100g快照时，以原有计算结果推导基础单位数据并保留原家用份量；不凭空添加其他单位。已保存的旧草稿不会重新落库。新版仍按同一草稿稳定id防重复。

21项相关测试通过：半份换算、单位切换、无效输入拦截、服务端忽略伪造热量、数量保存与历史状态恢复等。

真实云端编辑复测通过：原6个饺子、2碗饭改为3个饺子（75g/174kcal）与100g米饭（116kcal），确认保存至午餐。云端记录、刷新聊天后的输入数量/单位和合计均为290kcal；米饭旧的2碗标签已清除。测试创建的两条记录已清理。猫咪与森林主题编辑控件均已检查。

## 保存状态与餐次入口修复

聊天历史读取时按当前账号批量核对savedMeal.ids是否仍存在，显示active/partial/deleted状态。已清理或已删除的记录不再显示为仍然已保存。返回教练页会更新现有已保存卡片状态。保存卡片提供“查看日期+餐次记录”按钮，通过一次性pendingDietView导航到饮食页；饮食页在拉取记录前设置对应日期与餐次，避免默认早餐掩盖午餐记录。

排查本次反馈时，云端真实午餐416kcal存在，页面停在早餐；前两轮复测记录已清理但卡片标记残留，导致误导。本次不恢复自动测试记录、不改动用户实际饮食。
